# AI Execution Control Plane: Evolution from Model Platform to Task Execution Control Plane

**English** | [简体中文](ai-execution-control-plane.zh-CN.md)

> Status: research input (devdocs), not a product commitment  
> Observation date: 2026-09-16

## 1. Core thesis

AI Cloud should evolve beyond a Model Management Platform or Agent Platform into an **AI Task Execution Control Plane**. The first-class governed object should be the **Task**, not the Model or Agent.

It should connect four currently fragmented worlds: AI (Model/Agent/Memory/MCP/Evaluation), enterprise systems (Identity/Domain Data/API/Workflow/Governance), compute (GPU/NPU/PPU/K8s/VM/Bare Metal), and continuous learning (Task → Execution → Outcome → Evaluation → Organization Memory).

Core principle: **Model proposes; Policy permits; Runtime executes; Evaluation learns.** A prompt is not a permission boundary and a model does not own final execution authority.

## 2. Target architecture

```text
                         TASK
                           │
                     Task Planner
                           │
                     Policy Engine
                           │
                  Intelligent Router
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
          Model          Agent         Human
             │             │
             └──────┬──────┘
                    ↓
               Tool Registry
                    ↓
             Execution Runtime
        ┌───────────┼───────────┐
        ↓           ↓           ↓
       K8s          VM       Bare Metal
        │           │           │
        └───────────┼───────────┘
                    ↓
             GPU / NPU / PPU
                    │
                    ↓
             Execution Trace
                    │
                    ↓
                Evaluation
                    │
                    ↓
           Organization Memory
                    │
                    └──────────→ Next Task
```

The control plane declares what is allowed, who may perform it, which resources may be used, budget, and escalation rules. The execution plane reliably executes inside those constraints.

## 3. First-class resource model

Candidate API/CRD resources: `TaskDefinition`, `ModelProfile`, `AgentProfile`, `ToolDefinition`, `Policy`, `ExecutionPlan`, `ExecutionRun`, `MemoryObject`, `EvaluationProfile`, and `ResourceProfile`.

`TaskDefinition` captures goal, input, SLA, budget, risk and success criteria. `ExecutionPlan` is an auditable DAG generated by planning/routing. `ExecutionRun` records actual state, resources and checkpoints.

## 4. Model Registry 2.0

Upgrade the registry from a static catalog to an executable capability registry. In addition to parameters, context and benchmarks, track identity/provider/license, capability/modality/tool-use/reasoning, task success, token/cache pricing, TTFT, prefill/decode throughput, KV-cache footprint, HBM requirement, quantization, TP/PP, speculative decoding, GPU/NPU/PPU compatibility, vLLM/SGLang/TensorRT-LLM compatibility, data retention/residency/private deployment, task cost, reliability and observed failures.

The long-term economic metric should shift from `$ / token` toward **Cost per Successful Task**.

## 5. Intelligent Router 2.0

Routing becomes task-centric multi-objective optimization:

```text
Route = f(capability, modality, quality, latency, task_state,
          privacy, jurisdiction, license, hardware, cost,
          reliability, risk)
```

Support model, agent, tool and compute-resource routing. Planner creates candidates; Router selects a path; Policy Engine retains final authorization.

## 6. Policy Engine 2.0

Policy evolves from content filtering into Execution Authorization. It governs who can initiate a task, accessible domain data, models permitted for each data class, tool capabilities (read/write/delete/execute), human approval, token/GPU/monetary budgets, delegation depth, sub-agent count, network/filesystem/secrets boundaries, jurisdiction, residency and retention.

Credentials are injected by Runtime; models receive capabilities, not raw secrets.

## 7. Execution Runtime

Runtime is a key differentiator from application/framework layers. Required capabilities include Durable Execution, Checkpoint/Resume, Sandbox, Credential Broker, Network Policy, Filesystem Policy, Human-in-the-loop, Timeout, Budget Enforcement, Kill/Suspend, Replay and Immutable Audit.

Runtime must remain framework-neutral so LangGraph, CrewAI, custom agents and Codex-like harnesses can run as workloads.

## 8. Heterogeneous resource plane

Unify K8s, KubeVirt VM, Bare Metal and heterogeneous accelerators into a Resource Plane. Scheduling inputs should include model runtime, quantization, TP/PP, KV cache, data locality, startup time, cost and SLA—not only GPU count and VRAM.

## 9. Memory and continuous learning

Layer memory into Session, User/Team, Procedural and Organization Memory. Preserve governed execution trajectories rather than chat alone:

```text
Problem → Plan → Decisions → Tool calls → Execution
        → Feedback → Outcome → Evaluation → Reusable Procedure
```

Only evaluated, policy-compliant and appropriately sanitized trajectories may enter Organization Memory, preventing failed behavior from self-reinforcing.

## 10. Evaluation 2.0

Move from model benchmarks to task evaluation. Core metrics: Task Success Rate, Cost per Successful Task, Human Intervention Rate, Effective Autonomous Horizon, Recovery Rate, Tool Success Rate, Policy Violation Rate, P50/P95 Completion Time, Resource Efficiency and Memory Reuse Gain.

Evaluation feeds Router, Registry and Organization Memory. Production policy changes remain governed, auditable and rollbackable rather than autonomously modified by models.

## 11. Domain AI

Treat Domain AI as:

```text
General Intelligence
+ Domain Data
+ Domain Knowledge
+ Domain Tools
+ Domain Evaluation
+ Workflow
```

A future `Domain Pack` can package connectors, tools, policies, evaluation sets, procedures and agent templates while keeping the underlying model replaceable.

## 12. External product research mapping

Continuously study Microsoft Foundry Agent Service, AWS Bedrock AgentCore, Google Vertex AI Agent Engine, OpenAI agent runtimes, LangGraph, Dify and emerging security/runtime-first open-source projects.

The purpose is not feature copying but hypothesis validation: framework-neutral runtime, provider-neutral registry, hardware-neutral resource plane, policy independent from prompts/models, governed memory/learning loops, and Task as the unifying abstraction. Product/version claims should live in separate research notes and follow devdocs evidence rules.

## 13. Proposed iteration roadmap

### R1: Task Contract
Define `TaskDefinition / ExecutionPlan / ExecutionRun`. Wrap existing inference calls as Tasks and capture model, resource, cost and outcome telemetry.

### R2: Registry + Router
Upgrade Model Registry; implement provider-neutral routing; connect local vLLM/SGLang and at least two commercial providers; establish task-level quality/cost telemetry.

### R3: Tool + Policy + Runtime
Build Tool Registry, Credential Broker and Policy Engine; add sandbox, checkpoint, approval, kill, budget and audit. This is the first true Execution Control Plane milestone.

### R4: Heterogeneous Resource Plane
Unify K8s/VM/Bare Metal and GPU/NPU/PPU scheduling; join model runtime profiles with resource profiles for Task → Model → Runtime → Hardware scheduling.

### R5: Evaluation + Organization Memory
Introduce task evaluation and governed Procedural Memory. Optimize routing using historical quality/cost/reliability while keeping policy publication governed.

### R6: Domain Packs
Validate one or two real enterprise workflows combining Domain Data + Tools + Evaluation + Workflow. Demonstrate value as reliable business-task completion rather than model deployment count.

## 14. Product boundaries

Do not center differentiation on rebuilding a generic Agent Framework, low-code Dify equivalent, OpenAI-compatible gateway, GPU scheduler, or model-serving UI.

AI Cloud differentiation should be **Task-centric, Execution-first, Policy-native, Model/Framework/Cloud/Hardware-neutral, and Continuous-learning-ready**.

## 15. Next engineering outputs

Derive formal artifacts from this research rather than silently converting it into product commitments: an ADR for Task as a first-class resource; API specs for TaskDefinition/ExecutionPlan/ExecutionRun; Control/Execution/Resource Plane architecture; Execution Authorization policy spec; ModelProfile 2.0 registry spec; R1–R6 roadmap with acceptance criteria; and a PoC that closes the loop Task → Router → Agent → Tool → Runtime → Evaluation → Memory.
